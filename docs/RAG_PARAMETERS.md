# RAG 파라미터 설계 근거

모든 수치는 `embedding-service/eval/evaluate.py` 로 직접 측정한 값입니다.
평가셋은 데이터 문구를 그대로 쓰지 않고 **사용자 말투로 바꿔 쓴 질문 40개**(`eval/eval_set.jsonl`)와
**범위 밖 질문 6개**(`eval/ood_set.txt`)입니다.

> ⚠️ 평가셋이 40문항이라 질문 1개 = 2.5%p 입니다. 1~2%p 차이는 노이즈로 보고, 의미 있는 차이만 근거로 썼습니다.

## 1. 전체 구조

```
질문 ─┬─▶ [기관 필터] ─┬─▶ Dense (e5-small-ko, 코사인) ──┐
      │               └─▶ BM25 (한글 바이그램)  ──────────┴─▶ RRF 융합 ─▶ top-4 ─┬─▶ Claude 답변
      │                                                                    │
      └──────────────────── dense top-1 < 0.50 ? ──────────────────────────┴─▶ "범위 밖" 안내 (LLM 호출 X)
```

| 구성 요소 | 위치 |
|---|---|
| 질의 임베딩 사이드카 (FastAPI) | `embedding-service/app.py` |
| 문서 벡터 + Q&A 원본 | `backend/src/main/resources/data/qa_embeddings.jsonl` |
| 하이브리드 검색 | `backend/.../service/RetrievalService.java` |
| 설정값 | `backend/src/main/resources/application.yml` (`rag.*`) |

## 2. 측정 결과 요약

| 구성 | Hit@1 | Hit@3 | Hit@5 | MRR |
|---|---|---|---|---|
| BM25 단독 | 0.675 | 0.925 | 1.000 | 0.815 |
| Dense 단독 (제공 벡터) | 0.850 | 0.975 | 1.000 | 0.918 |
| Dense 단독 (로컬 재인코딩) | 0.900 | 0.975 | 0.975 | 0.940 |
| Dense, `query:` 접두어 없이 | 0.875 | 0.975 | 1.000 | 0.926 |
| 가중합 α=0.8 (min-max) | 0.875 | 0.975 | 1.000 | 0.930 |
| RRF k=60 | 0.875 | 1.000 | 1.000 | 0.938 |
| **RRF k=60 + 기관명 자동 필터 (채택)** | **0.900** | **1.000** | **1.000** | **0.950** |
| ↳ 같은 구성, Java API 실측 | 0.875 | 1.000 | – | 0.938 |

Java 실측이 1문항 낮은 이유: Python `\w` 와 Java `\p{L}\p{N}` 토큰 분리가 "4개월" 같은 숫자+한글 어절에서 미세하게 달라 BM25 순위가 한 칸 바뀜 (`여권 만료일...` 질문, 정답은 2위).

## 3. 파라미터별 근거

### 임베딩 모델 — `dragonkue/multilingual-e5-small-ko-v2` (384차원)
- **문서 벡터를 만든 모델과 반드시 같아야 함.** 다른 모델로 질문을 임베딩하면 벡터 공간이 달라 유사도가 무의미해집니다.
- small(약 118M 파라미터, 465MB)이라 CPU 에서도 질문 1개 임베딩이 약 12~20ms (로컬 실측) → 로컬 실행에 적합.

### 문서 벡터 — 제공된 벡터를 그대로 사용 (재인코딩 안 함)
- 로컬에서 `"passage: " + embed_text` 로 다시 만든 벡터와 제공 벡터의 코사인은 평균 **0.98** (1.0 아님 → 모델 리비전/런타임 차이로 추정).
- 재인코딩 시 Dense 단독 Hit@1 은 +5%p, Hit@5 는 −2.5%p 로 엇갈렸고, **최종 하이브리드 구성에선 차이가 없거나 제공 벡터가 근소 우위** (MRR 0.950 vs 0.944).
- → 원본 데이터의 재현성을 우선해 제공 벡터 사용. 데이터가 바뀌면 같은 모델로 재생성하면 됩니다.

### 질의 접두어 — `"query: "`
- E5 계열은 질의 `query:` / 문서 `passage:` 비대칭 접두어로 학습됐고, 제공된 `search_example.py` 도 같은 규칙을 씀.
- 실측에서 접두어를 빼도 큰 차이는 없었지만(MRR 0.926 vs 0.918, 1문항 차이), 모델 학습 규약을 따르는 쪽이 데이터가 늘었을 때 안전합니다.

### `max_seq_length = 256`
- 데이터 최대 길이 127 토큰, 평균 84 토큰. 512 대비 잘림 없이 어텐션 연산량을 줄입니다. 질문은 1000자로 입력 제한.

### 하이브리드 검색 (Dense + BM25)
- Dense 는 "짐 몇 키로 무료로 부쳐요" ↔ "무료 위탁 수하물 허용량" 같은 **말 바꿈**에 강하고,
  BM25 는 "수수료안심플러스", "Ultra Lite", "땡처리" 같은 **고유명사·상품명**에 강합니다.
- 융합 후 Hit@3 이 0.975 → **1.000** 으로 올라, LLM 컨텍스트에 정답이 빠지는 경우가 사라졌습니다.

### 융합 방식 — RRF, `rrf-k: 60`
- BM25 점수(0~수십)와 코사인(0~1)은 척도가 달라 가중합은 min-max 정규화가 필요하고, 정규화는 질의마다 분포가 흔들립니다.
  실측에서도 가중합(α=0.5~0.8)은 MRR 0.898~0.930 으로 RRF(0.938)보다 낮았습니다.
- RRF 는 순위만 쓰므로 정규화가 필요 없음. k=20 과 k=60 은 동일 성능 → 상위 순위 한 칸 차이에 덜 민감한 **표준값 60** 채택.

### `candidate-pool: 50`
- 각 검색기에서 융합에 올릴 후보 수. 지금은 83건이라 사실상 전체이지만, 데이터가 수천 건으로 늘어도 융합 비용을 고정하기 위한 상한입니다.

### `auto-org-filter: true`
- 질문에 "대한항공", "제주항공" 처럼 기관명이 있으면 해당 기관 문서로 한정합니다. 같은 주제(수하물, 환불)가 기관마다 반복되는 데이터라
  **다른 기관의 비슷한 답이 끼어드는 것**을 막는 효과가 크고, Hit@1 이 0.875 → 0.900 으로 올랐습니다.
- 사용자가 칩으로 기관을 고르면 그 선택이 우선합니다.

### `top-k: 4` (LLM 컨텍스트 문서 수)
- 채택 구성에서 정답 순위는 **40문항 모두 2위 이내**(1위 36, 2위 4). 2배 여유를 둬 4로 설정.
- 더 늘리면 다른 기관의 비슷한 Q&A 가 섞여 답변이 흐려지고 토큰만 늘어납니다. Q&A 1건 평균 111자라 4건이면 컨텍스트가 짧습니다.

### `dense-min-score: 0.50` (범위 밖 판정)
- 범위 안 질문의 dense top-1 코사인: 최소 **0.543**, 하위 10% 0.669, 중앙값 0.721
- 범위 밖 질문: 날씨 0.453 · 비트코인 0.457 · 김치찌개 0.397 · 파이썬 0.407 · 삼성전자 0.392 · **아시아나 마일리지 0.576**
- 0.50 은 범위 안 최솟값(0.543)보다 낮아 **정상 질문을 하나도 막지 않으면서** 범위 밖 6개 중 5개를 LLM 호출 없이 차단합니다.
- 아시아나 질문처럼 "항공 주제지만 데이터에 없는 기관"은 임계값을 통과합니다. 이건 2차 방어선인 프롬프트
  ("자료에 없으면 확인되지 않는다고 말할 것")가 처리합니다. 임계값을 0.58 이상으로 올리면 이 질문도 막히지만 정상 질문 일부(0.543~0.58)가 같이 막힙니다.
- BM25 점수는 기준으로 쓰지 않습니다: 범위 밖 "날씨" 질문의 BM25 top-1(13.3)이 범위 안 최솟값(9.1)보다 높아 판별력이 없었습니다.

### 임베딩 서비스 장애 시 — BM25 단독 폴백 (`timeout-ms: 3000`)
- 사이드카가 꺼져 있거나 3초 안에 응답하지 않으면 BM25 만으로 검색합니다 (Hit@3 0.925 로 서비스는 유지).
- 이때는 범위 밖 판정을 하지 않고 프롬프트에 맡기며, 화면에 "키워드 검색 결과" 배지를 표시합니다.
- 3초는 첫 요청의 모델 워밍업을 감안한 값입니다(이후 요청은 약 12~20ms).

### BM25 — `k1=1.2`, `b=0.75`, 질문 필드 3배 가중
- Lucene/Elasticsearch 기본값. 문서가 짧고 길이가 고른(평균 111자) FAQ 라 튜닝 여지가 작아 표준값 사용.
- 한국어 형태소 분석기 없이 **어절 + 글자 바이그램**으로 색인해 "체크인은/체크인을" 같은 조사 변화를 흡수합니다.
- 사용자 질문은 데이터의 '질문' 문장과 어휘가 겹칠 가능성이 높아 `기관명 + 질문` 필드를 3배 가중합니다.

### LLM — `claude-opus-5-5`, `max-tokens: 2000`, `effort: low`, `history-turns: 3`
- 답변은 Q&A 몇 건을 짧게 요약하는 작업 → 깊은 추론보다 응답 속도가 중요해 effort `low`.
- 답이 길어도 수백 자라 2000 토큰이면 잘림 없이 충분합니다.
- 최근 3왕복만 넘겨 "그럼 국내선은요?" 같은 후속 질문 맥락은 유지하고 토큰은 아낍니다.
- 범위 밖 질문은 LLM 을 부르지 않아 환각과 비용을 함께 줄입니다.

### 후속 질문 — `followup-carry-org: true`, `followup-short-chars: 8`
대화 히스토리는 LLM 에만 넘어가고 **검색**은 현재 질문만 쓰고 있어서, "기내는요?" 같은 후속 질문은 주제도 기관도 없이 검색됐습니다.
후속 질문 16개(`eval/followup_set.jsonl`, 직전 질문 + 현재 질문 + 정답)로 전략을 비교했습니다 (`eval/evaluate_followup.py`).

| 전략 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|
| S0 현재 질문만 (기존) | 0.500 | 0.750 | 0.653 |
| S1 기관 이어받기 | 0.688 | 0.812 | 0.769 |
| **S2 S1 + 8자 미만이면 직전 질문과 결합 (채택)** | **0.812** | **1.000** | **0.885** |
| S2 S1 + 12·16·20자 미만이면 결합 | 0.625 | 0.938 | 0.776 |
| S3 S1 + 항상 결합 | 0.625 | 0.938 | 0.776 |
| ↳ 채택 구성, Java API 실측 | 0.812 | 1.000 | – |

- **기관 이어받기**: 현재 질문에 기관명이 없으면 직전 질문의 기관으로 필터합니다. 현재 질문에 기관명이 있거나("대한항공은요?") 칩으로 고른 기관이 있으면 그쪽이 우선합니다.
- **짧은 질문만 결합**: "기내는요?", "위탁은요?"처럼 주제를 생략한 질문은 직전 질문과 합쳐야 찾을 수 있습니다.
  반대로 "카운터는 언제 마감해요?"처럼 자기 주제가 있는 질문까지 합치면 직전 주제(체크인)가 섞여 순위가 흐려졌습니다 (항상 결합 시 Hit@1 0.625).
- **8자 기준**: 공백 제외 길이로 주제 생략형(5~7자)과 완결형(8자 이상)이 갈렸습니다. 다만 16문항 기준이라 과적합 가능성이 있어, 후속 질문 로그가 쌓이면 다시 측정해야 합니다.
- 단일 질문 평가셋(40개)은 히스토리가 없어 결과가 그대로입니다 (Java API 재측정 Hit@1 0.875, Hit@3 1.000).

## 4. 재평가 방법

```bash
cd embedding-service
.venv/bin/python eval/evaluate.py           # 단일 질문: 검색기·융합·임계값
.venv/bin/python eval/evaluate_followup.py  # 후속 질문: 멀티턴 검색 전략
```

데이터나 파라미터를 바꾸면 위 스크립트를 다시 돌려 표를 갱신하세요. 평가셋은 `eval/eval_set.jsonl`, `eval/followup_set.jsonl` 에 질문과 정답 id 를 추가하면 됩니다.
